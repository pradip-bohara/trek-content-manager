**Plugin Audit Report**

I reviewed the complete `Trek Content Manager` plugin: PHP classes, templates, JavaScript, CSS, importer, REST API, shortcodes, roles, and map functionality.

**Critical Issues**

1. **Public shortcode can expose private or unrelated posts**

   `[trek_destination id="123"]` does not verify post type, post status, or user permission. Visitors may request drafts, private posts, or another post type.

   Fix in `trek-content-manager.php:196` and `single-trek_destination.php:9`: allow only published `trek_destination` posts unless the current user can edit them.

2. **Anonymous users can publish approved reviews**

   Public users can submit reviews that are immediately saved as `publish` and `_trek_approved = 1`.

   See `class-trek-rest-api.php:130`.

   Fix:

   - Save reviews as `pending`
   - Validate that `trek_id` is a published destination
   - Add CAPTCHA, rate limiting, duplicate detection, and email validation
   - Approve reviews only from the WordPress admin

3. **REST destination save endpoint accepts unsafe/incomplete data**

   Only `title` and `overview.intro` are sanitized. The remaining JSON is stored almost unchanged.

   See `class-trek-rest-api.php:95`.

   Fix:

   - Validate the destination post type
   - Require a dedicated capability such as `edit_trek_destinations`
   - Sanitize every field according to its context
   - Reject unknown fields
   - Limit payload size and nested array depth

4. **JavaScript has potential stored XSS**

   The engine inserts data using `innerHTML`, including text, URLs, attributes, and image sources.

   See `trek-engine.js:295`.

   Fix: use `textContent`, DOM APIs, and strict URL validation. Do not interpolate database or user data directly into HTML strings.

5. **Importer permissions are too broad**

   The importer only requires `edit_posts`, but it can create, update, and publish destinations.

   See `class-trek-importer.php:671`.

   Fix: require `manage_trek_content` or a separate `import_trek_content` capability. Separate importing from publishing permission.

**Major Functional Problems**

6. **Two incompatible rendering systems exist**

   The PHP template and JavaScript engine use different data structures and DOM IDs.

   PHP uses fields such as:

   - `quick_facts`
   - `reviews_section`
   - `itinerary`
   - `gallery`

   JavaScript expects:

   - `keyFacts`
   - `geography`
   - `reviews`
   - `included`
   - `packingList`

   The engine therefore cannot reliably render the data produced by the PHP renderer.

   See `class-trek-renderer.php:47` and `trek-engine.js:35`.

   Recommendation: choose one rendering architecture. The simplest route is to keep PHP rendering as the primary system and remove or redesign the unused JavaScript renderer.

7. **Importer writes different meta keys from the visible template**

   The importer writes:

   - `_trek_itinerary`
   - `_trek_gallery_images`
   - `_trek_faqs`
   - `_trek_inclusions`

   The template primarily reads:

   - `_trek_itinerary_list`
   - `_trek_gallery_list`
   - `_trek_essential_list`
   - `_trek_inclusions_list`

   Imported itinerary, gallery, FAQs, and inclusion data may not appear on the public page.

   See `class-trek-importer.php:884` and `single-trek_destination.php:105`.

8. **Curated reviews use inconsistent keys**

   Admin saving uses `_trek_curated_reviews`, while the renderer looks for `_trek_reviews_list`.

   See `class-trek-cpt.php:2003` and `class-trek-renderer.php:349`.

9. **JavaScript overwrites real WordPress context**

   WordPress correctly localizes the logged-in user role, nonce, REST URL, and current post ID. The JavaScript immediately replaces that object with demo defaults.

   See `trek-content-manager.php:136` and `trek-engine.js:18`.

   This can cause incorrect role controls, wrong destination IDs, and demo data appearing on production pages.

10. **Enquiry API returns success without processing the enquiry**

    The endpoint validates the email and then returns success. It does not save the enquiry, send email, or notify WhatsApp.

    See `class-trek-rest-api.php:111`.

    Fix by storing enquiries as a custom post type or database record and sending an admin notification.

11. **Shortcode instances generate duplicate HTML IDs**

    Multiple `[trek_destination]` shortcodes on one page will reuse IDs for forms, tabs, lightboxes, and controls.

    Fix by generating a unique instance ID and prefixing all DOM IDs and selectors.

12. **Map depends on an external unpinned GeoJSON file**

    The Nepal map loads GeoJSON from GitHub at runtime and depends on D3 without clearly bundling or declaring it.

    See `nepal-map-template.php:923`.

    Fix by bundling a pinned D3 version and serving validated GeoJSON locally.

**Security and Data Concerns**

- Review email addresses are stored in plaintext.
- Reviews have no spam protection or rate limiting.
- Review `trek_id` is not validated.
- Importer has no clear upload-size, item-count, JSON-depth, or memory limits.
- Import counters are incremented before confirming database success.
- Generic WordPress capabilities and custom Trek capabilities are inconsistent.
- REST output can expose data from any published destination without a clear field-level privacy policy.
- Deactivation removes capabilities but does not flush rewrite rules.
- Image URLs are accepted from external domains without allowlisting.

**SEO Problems**

- The renderer claims canonical support but does not output a canonical URL.
- Breadcrumb URLs are hardcoded to `/all-trips/` and `/destinations/`.
- Schema values are HTML-escaped before JSON encoding.
- `GovernmentPermit` is questionable as a Schema.org type.
- Default synthetic reviews are included when no real reviews exist, which can create misleading review markup.
- Multiple JSON-LD blocks may conflict with SEO plugins.

See `class-trek-renderer.php:428`.

**Accessibility and Performance**

- Tabs lack complete keyboard handling and panel relationships.
- Map regions need keyboard activation and stronger focus states.
- Multiple inline scripts and styles are emitted.
- Several listing queries use `posts_per_page => -1`.
- Review queries are repeated without caching.
- External Google Fonts and full-size remote images can slow initial rendering.
- Duplicate event handlers and global selectors become problematic with multiple shortcodes.

**Plugin Parts**

- `trek-content-manager.php`: bootstrap, hooks, assets, template override, main shortcode
- `class-trek-cpt.php`: custom post types, taxonomies, admin fields, metadata saving
- `class-trek-roles.php`: role mapping and capabilities
- `class-trek-rest-api.php`: destination API, enquiries, reviews
- `class-trek-renderer.php`: normalized data, SEO, Open Graph, JSON-LD
- `class-trek-shortcodes.php`: trip listings, filters, journey finder, maps
- `class-trek-importer.php`: JSON import and sample data
- `single-trek_destination.php`: public destination page
- `nepal-map-template.php`: interactive Nepal map
- `trek-engine.js`: client-side demo/rendering engine
- `trek-roles.js` and `trek-validation.js`: browser role and validation helpers
- `trek-detail.css`: public visual styling

**Recommended Work Order**

1. Fix shortcode post type/status authorization.
2. Fix review moderation and spam protection.
3. Secure the REST save endpoint and importer permissions.
4. Select one rendering architecture.
5. Define one canonical metadata schema and migrate importer/template/renderer to it.
6. Remove the JavaScript demo defaults from production.
7. Fix duplicate shortcode IDs.
8. Implement real enquiry storage and notification.
9. Fix SEO schema and canonical URLs.
10. Add automated tests for permissions, XSS, importer mapping, reviews, and multiple shortcode instances.

**Validation**

All PHP files passed `php -l`, and all JavaScript files passed `node --check`. No static syntax errors were found. There are currently no PHPUnit, integration, browser, or accessibility tests, so runtime testing in WordPress is still required before production use.
